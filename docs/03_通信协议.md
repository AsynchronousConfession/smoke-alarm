# 03 通信协议（节点 ↔ 网关 ↔ 云）

整条链路一共有两种协议：**BLE GATT**（节点↔网关）和 **MQTT**（网关↔云）。

---

## 一、BLE 部分（节点 ↔ 网关）

### 1.1 角色与连接

| 项目 | 值 |
|---|---|
| 节点角色 | Peripheral（外设从机），广播名 `SMOKE_NODE` |
| 网关角色 | Central（主机），主动扫描并连接 |
| 连接间隔 | 节点期望 7.5~125ms，网关连上后 4 秒发起一次参数更新 |
| MTU | 默认 23 → 单次 Notify / Write 最多 **20 字节** |
| 从机数量 | 每个节点独占一条连接；网关用 `APP_MAX_NODES` 限制（默认 4） |

广播/扫描响应内容：

```
ADV_IND : Flags + 16bit Service UUID 0xFFE0
SCAN_RSP: 完整设备名 "SMOKE_NODE" + 连接间隔范围 + 发射功率
```

> 网关只按**设备名**过滤（`APP_NODE_ADV_NAME`），不按服务 UUID 兜底，
> 以免连到旁边实验室里同样用 0xFFE0 的沁恒板子（代码里 `MASTER_MATCH_BY_UUID_FALLBACK = 0`）。

### 1.2 GATT 服务

沿用沁恒 SimpleProfile（服务 UUID `0xFFE0`），两侧约定：

| 特征 | UUID | 属性 | 方向 | 用途 |
|---|---|---|---|---|
| CHAR1 | 0xFFE1 | Read/Write | — | 预留 |
| CHAR3 | 0xFFE3 | Write | 网关 → 节点 | 下发命令/文本，长度 20 字节 |
| CHAR4 | 0xFFE4 | Notify | 节点 → 网关 | 遥测帧 / 信息帧，长度 ≤20 字节 |

### 1.3 遥测帧（16 字节，小端）

> 为什么用二进制不用 JSON？因为默认 MTU 只有 23（负载 20 字节），JSON 一个字段就超了。

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | magic | 固定 `0x53`（字符 `'S'`，Smoke） |
| 1 | 1 | type | `0x01` = 遥测 |
| 2 | 1 | seq | 序号，0~255 循环，用来粗查丢包 |
| 3 | 1 | flags | bit0 报警 · bit1 预热中 · bit2 DO 为高 · bit3 已消音 |
| 4 | 2 | adc | ADC 原始值 0~4095 |
| 6 | 2 | ao_mv | 模块 AO 电压（mV） |
| 8 | 4 | rs | 传感器等效电阻 Rs（Ω） |
| 12 | 2 | dpct | Δ% ×10（有符号），例如 `-523` = −52.3% |
| 14 | 1 | do | DO 引脚电平 0/1 |
| 15 | 1 | sum | 前 15 字节求和取低 8 位（校验） |

### 1.4 信息帧（20 字节）

上电连上后发送、之后每 30 秒补发一次，用于告诉网关"我是谁"：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1 | `0x53` |
| 1 | 1 | `0x02` = 信息 |
| 2 | 18 | ASCII `"节点编号|型号|版本"`，例如 `N01|MQ-2|1.0`，不足补 `0x00` |

### 1.5 下行命令（写 0xFFE3，ASCII，≤20 字节）

| 命令 | 含义 |
|---|---|
| `M` / `MUTE` | 消音 60 秒（报警判定和上报照常，只是本机蜂鸣器不响） |
| `M30` | 消音 30 秒（`M` 后面跟数字即秒数，上限 3600） |
| `T` / `TEST` | 自检：蜂鸣器长鸣 3 秒 |
| `R` / `RESET` | 清除报警锁存（基线不动，安全第一） |
| 其它字符串 | 只在节点串口日志里打印一行（节点只有单片机 + 传感器 + 蜂鸣器，没有屏幕） |

### 1.6 节点上报节奏

| 状态 | 采样 | 上报 |
|---|---|---|
| 正常 | 500ms | 2s |
| 报警 | 500ms | **0.5s** |
| 预热（前 30s） | 500ms | 2s，flags 带 warmup 位，不判报警 |

## 二、MQTT 部分（网关 ↔ 云）

### 2.1 主题设计

前缀 `home/<gateway_id>`，`<MAC>` 是 12 位十六进制（无冒号，如 `AABBCCDDEEFF`）。

| 主题 | 方向 | QoS | retain | 说明 |
|---|---|---|---|---|
| `home/gw01/tele/<MAC>` | 上行 | 1 | 否 | 遥测数据（约 2s 一条） |
| `home/gw01/event/<MAC>` | 上行 | 1 | 否 | 报警 / 解除事件 |
| `home/gw01/state/<MAC>` | 上行 | 1 | **是** | 节点在线状态 + 编号/型号/版本 |
| `home/gw01/state/gateway` | 上行 | 1 | **是** | 网关心跳（IP/WiFi 信号/在线节点数） |
| `home/gw01/ack/<MAC>` | 上行 | 1 | 否 | 指令回执（ok=true/false） |
| `home/gw01/cmd/<MAC>` | 下行 | 1 | 否 | 控制指令，纯文本 |

**为什么要 retain**：状态类消息只要保留最后一条，网页任何时候打开都能立刻知道"谁在线"，
不用等下一次心跳。网关注册了**遗嘱消息（LWT）**：`{"online":false}`，
这样网关异常掉电时，Mosquitto 会立刻帮它发一条"我离线了"。

### 2.2 报文格式

遥测（`tele`）：

```json
{"ts":1790933403,"mac":"AABBCCDDEEFF","seq":12,"adc":1035,"ao":1668,
 "rs":1998,"dpct":-52.3,"alarm":1,"warmup":0,"do":0,"muted":0,"rssi":-45}
```

报警事件（`event`）：

```json
{"ts":1790933403,"mac":"AABBCCDDEEFF","kind":"alarm","dpct":-52.3,
 "rs":1998,"adc":1035,"rssi":-45}
```

`kind` 取值 `alarm`（报警出现）/ `clear`（报警解除）。

节点状态（`state`）：

```json
{"ts":1790933403,"mac":"AABBCCDDEEFF","online":true,"rssi":-45,
 "tag":"N01","model":"MQ-2","fw":"1.0"}
```

网关心跳（`state/gateway`）：

```json
{"ts":1790933403,"online":true,"ip":"192.168.137.1","wifi_rssi":-50,
 "nodes":3,"nodes_max":4,"fw":"1.0"}
```

字段含义：

| 字段 | 含义 | 单位 |
|---|---|---|
| `ts` | 时间戳（网关 SNTP 同步；没同步上发 0，后端补当前时间） | 秒 |
| `adc` | ADC 原始值 | 0~4095 |
| `ao` | 模块 AO 电压 | mV |
| `rs` | 传感器等效电阻 Rs | Ω |
| `dpct` | 相对自适应基线的变化，**负值 = 电阻变小 = 闻到可燃气/烟雾** | % |
| `alarm` | 是否报警 | 0/1 |
| `warmup` | 是否还在预热 | 0/1 |
| `muted` | 是否已消音 | 0/1 |
| `rssi` | 网关测到的该节点 BLE 信号强度 | dBm |

### 2.3 ACL（权限）

Mosquitto 的 ACL 由 `server\setup.ps1` 自动生成：

```
user backend      # 后端
topic read  home/#
topic write home/+/cmd/+

user esp32gw      # ESP32 网关
topic write home/+/tele/+
topic write home/+/event/+
topic write home/+/state/+
topic write home/+/ack/+
topic read  home/+/cmd/+
```

即：**设备只能写自己的上报主题、只能读命令主题；后端能读全部、只能写命令主题**。

## 三、HTTP 接口（网页 ↔ 后端）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/status` | 网关状态 + 全部节点当前值 |
| GET | `/api/series?mac=&hours=&since=&max_points=` | 某节点近 N 小时的 Δ% 曲线。`hours` 支持小数（0.5=30 分钟）；带 `since` 时只返回该时间之后的新点（前端每 2 秒增量刷新就靠它）；点太多时自动抽稀到 `max_points` 以内 |
| GET | `/api/events?limit=&mac=` | 事件流（默认 60 条） |
| GET | `/api/stats?hours=24` | 每小时报警次数统计 |
| GET | `/api/stream` | SSE 实时推送 |
| POST | `/api/cmd` | `{"mac":"…","text":"M"}` 下发指令 |

鉴权：所有 `/api/*` 需要请求头 `X-Auth: <访问口令>`（SSE 用 `?token=`）。

### 曲线是怎么做到"实时更新"又不卡的

1. 节点每 2 秒上报一次（报警时 0.5 秒），网关照发；后端按 `limits.tele_store_sec`（默认 **2 秒**）
   把一个点写进 `telemetry` 表；
2. 后端立刻通过 SSE 把**带数值的** `tele` 消息推给网页：
   `{"type":"tele","mac":…,"ts":…,"dpct":…,"adc":…,"ao":…,"rs":…,"rssi":…,"alarm":…}`；
3. 网页收到后：卡片**就地打补丁**更新，正在看的曲线**直接把点追加进本地缓存并重绘**——
   这一步 **0 次 HTTP 请求**；
4. 只有"兜底校准"才发请求：状态每 **15 秒**一次、曲线增量每 **30 秒**一次；
   切换节点/时间范围时按 `(节点, 时间范围)` 缓存**立刻出图**，再在后台增量补点；
5. 整段加载时后端会把超量数据抽稀到 `limits.series_max_points`（默认 1500）以内；
   也可以加 `fmt=2` 让点以 `[ts, dpct, alarm]` 数组返回，体积约为对象形式的 **1/3**。

> ⚠️ 早期版本是"每收到一帧遥测就 GET 一次 `/api/status`"。在公网隧道上单次请求可能长达 1.5 秒，
> 多节点时形成请求风暴，表现为"点一下要等很久"。改成**推送驱动**后请求量下降约两个数量级。

所以"实时性"和"服务器压力"是分开控制的：想更密就调小 `tele_store_sec`，想省资源就调大它。
自检脚本：`server\tools\check_speed.py`（会打印实测的曲线分辨率与增量点）。

## 四、两侧协议文件必须同步修改

BLE 帧格式在两个地方各有一份定义，**改协议时两边一起改**：

| 侧 | 文件 |
|---|---|
| 节点 | `node_ch573f\node\SmokeNode\APP\include\node_proto.h` |
| 网关 | `gateway_esp32s3\main\node_proto.h` |

MQTT 主题的约定在：

| 侧 | 文件 |
|---|---|
| 网关 | `gateway_esp32s3\main\wifi_mqtt.c` + `app_config.h` |
| 云端 | `server\backend\app.py` 顶部的主题注释 |
