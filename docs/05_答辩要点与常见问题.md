# 05 答辩要点与常见问题

## 一、三个"必须能说清"的核心问题

### Q1：为什么用 BLE 主从，不用 Mesh 或者广播？

**答（先结论，再理由，最后说边界）**：

* 结论：家用室内场景节点少（3~6 个）、距离近（十几米）、有常电，**主从星型**是性价比最高的方案。
* 理由一（可行性）：沁恒 CH57x 的 BLE 协议栈只提供外设/广播角色，**没有 Mesh 模型**
  （没有 provisioning、relay、元素模型），要上 Mesh 相当于自己写一套协议栈；
* 理由二（必要性）：Mesh 的核心价值是"多跳 + 自愈"，代价是每个节点都要参与转发、
  维护路由表、常开接收。本场景节点离网关都很近，用不到多跳；
* 理由三（功能）：本系统必须支持**下行指令**（消音/自检/复位），广播是单向的，做不到；
  而且广播包没有链路层确认，丢包无法补救，而连接态的 Notify 有 ACK + 重传；
* 边界：如果将来做整栋楼（几十个节点、跨楼层），就该换成 Mesh，或者"星型 + 中继"的混合结构。

### Q2：报警是怎么判出来的？为什么不用固定阈值？

**答**：

* 传感器输出是模拟量，直接看 AO 电压会因为**温湿度、供电、器件离散性、老化**而漂移，
  固定阈值要么天天误报，要么闻不到；
* 本系统用**自适应基线 + 相对变化率**：
  1. `Rs = RL × (VCC − Vao) / Vao`，把电压换算成传感器等效电阻（这是一种气体传感器的标准做法）；
  2. 基线 `Rs0` 每个采样点最多跟随 1%（`NODE_BASE_STEP_PM`）——分钟的漂移跟得上，
     几秒钟的气体事件跟不上；
  3. `Δ% = (Rs/Rs0 − 1) × 100`，`|Δ%| ≥ 25%` 连续 2 次 → 报警；
     回落到 12% 以下连续 5 次 → 解除（**迟滞**，防止在阈值附近抖来抖去）；
* 好处：换传感器、换环境都能自适应；坏处：传感器长期被污染时基线会被"带跑"，
  所以提供了 `R` 复位指令和"预热期不判定"的保护。

### Q3：为什么用二进制帧，不用 JSON？

**答**：BLE 默认 MTU 是 23 字节，单次 Notify 最多 20 字节负载。
一个 `{"dpct":-52.3}` 就 16 字节了，其余字段放不下。所以设计成 **16 字节定长二进制帧**：
小端整数 + 1 字节校验和，解析只需几次移位；MQTT 那一层带宽充裕，才用 JSON（可读、好调试）。

## 二、系统设计类问题

**Q：几个节点同时报警，网关忙得过来吗？**
A：单个节点正常 2 秒 1 帧、报警 0.5 秒 1 帧；4 个节点全报警也只有 8 帧/秒，
每帧 16 字节，BLE 与 WiFi 由 ESP32 的软件共存（`CONFIG_ESP_COEX_SW_COEXIST_ENABLE`）仲裁，
实测稳定。真正的瓶颈在数据库写入，所以后端做了**可调的入库节流**（默认曲线点 2 秒一条，
报警跳变立刻补一条），前端再用 `since` 做**增量拉取**（每 2 秒只取新点），
这样曲线既跟得上节点上报节奏，又不会把服务器刷爆；
长时段（比如近 24 小时）由后端自动等间隔抽稀到 1500 点以内，保证画得动。

**Q：节点掉线、网关掉线、家里断网分别会怎样？**
A：见 `docs/01` 第 5 节。要点是：**报警判定和蜂鸣器都在节点本地**，
断网不影响本机报警；网关有断网缓存（32 条）补发；平台靠心跳超时判离线。

**Q：怎么保证"哪个 MAC 是哪个房间"？**
A：三重标识（`docs/01` 第 3 节）：MAC 是唯一键，标签 A/B/C 由后端自动分配，
`NODE_TAG`（如"厨房"）是烧固件时填的、最直观。三者同时显示在卡片上，插拔换板也不会乱。

**Q：为什么后端不用 FastAPI/Django？**
A：本机是 32 位 Python 3.9，pydantic-core 没有预编译 wheel，装 FastAPI 会要求现场编译 Rust。
改用标准库 `http.server` + `sqlite3` + 纯 Python 的 `paho-mqtt`，
依赖只有一个 wheel（包内已自带，可离线安装），在毕设场景下更稳。

**Q：安全性怎么考虑？**
A：
* MQTT 用账号密码 + ACL（设备只能写自己的上报主题、只能读命令主题；后端能读全部、只能写命令）；
* 1883 只在内网监听，公网只通过 Cloudflare 隧道出去（**出站连接，不需要公网 IP、不开路由器端口**）；
* 网页有访问口令，云端 API 全部要 `X-Auth`；
* 隧道 token 与口令都放在 `server\config.json`，只在本机保存，不写进固件。

## 三、实现细节类问题

**Q：CH573F 只有 18KB RAM，你怎么塞下 BLE + 传感器 + 蜂鸣器的？**
A：BLE 协议栈占 6KB（`BLE_MEMHEAP_SIZE`），剩下的主要是应用层的小缓冲；
节点的硬件只有 MCU + MQ 传感器 + 蜂鸣器，**OLED 和按键相关的驱动代码全部删掉了**
（不是"编译时关掉"，是源码里就没有），所以没有任何无效开销。
编译结果：FLASH 用 27.3%（125120/458752）、RAM 用 71.9%（13244/18432），还有余量。
想做低功耗版本时，这部分余量就是留给休眠/唤醒逻辑的。

**Q：节点一共只有 8 个 ADC 引脚，你怎么分配？为什么调试串口用 PB4/PB7？**
A：CH573F（QFN28）可用的 ADC 引脚只有 8 个：PA4/PA5/PA8/PA9/PA12~PA15。
本系统按"够用 + 好接线"分配：**AO=PA4（AIN0）、DO=PA5、蜂鸣器=PB15**，
PA8/PA9/PA12~PA15 全部留空，以后想再挂一路 MQ-135 只要改 `node_cfg.h` 两行。
调试串口用 **UART0（PB4/PB7）**：与沁恒 `CH573F_MQ2_ADC_UART0` 例程的接线一致，
接线最好找，也不占用任何 ADC 脚。
顺带说明：`printf` 要能出到 UART0，是因为沁恒 SDK 的 `_write()` 用 `DEBUG` 宏选串口
（`DEBUG=0` 就是 UART0），工程在 `.cproject` 和编译脚本里都设成了 0。

**Q：帧里的序号和校验和有什么用？**
A：序号用于粗查丢包率（也可以做成滑动窗口统计），校验和用于丢弃被干扰破坏的帧。
BLE 链路层本身有 CRC，但应用层再加一层，成本只有 1 字节，能覆盖"解析层被写坏"的情况。

**Q：为什么报警时上报周期变成 0.5 秒？**
A：报警是要人立刻反应的场景，云端/网页需要快速看到趋势；而正常时 2 秒一帧足够画曲线，
还能省 BLE 带宽与 MCU 功耗。

## 四、现场演示的建议流程（5 分钟）

1. **先展示不上电的实物**：说明一个节点 = CH573F 最小系统板 + MQ-2 传感器（蜂鸣器可选），成本低；
2. **上电**：节点串口打印配置与每秒一行数据，30 秒预热结束时蜂鸣器"嘀"一声；
   网关串口打印"发现节点→连接→订阅"；
3. **打开网页**：指出卡片上的 Δ%、Rs、信号强度、在线状态（数据是真实的，不是录屏）；
4. **打火机测试**：节点蜂鸣器响 → 网页红色横幅 + 曲线掉到 -50% + 事件流出现"报警"；
5. **点"消音 60s"**：蜂鸣器停，事件流出现回执 → 说明下行链路通了；
6. **拔掉一个节点**：串口提示断开、网页变离线 → 说明系统能自恢复，然后再插回去；
7. **手机用流量打开公网地址**：说明"上云"是真的（走 Cloudflare 隧道）。

## 五、已知不足与改进方向（答辩时主动说出来是加分项）

| 不足 | 说明 | 改进方向 |
|---|---|---|
| MQ 系列是**半定量**传感器 | 只能给出"相对变化"，不能直接给 ppm；且需要预热、会老化 | 换标定后的数字传感器（如 SGP30/CCS811 做空气质量、TGS 系列做定量）；或对每种气体做标定曲线 |
| 电脑关机时不入库 | 家用的固有代价（无云端付费服务） | 网关接 SD 卡缓存；或换成便宜的云服务器/MQTT 公有云 |
| 断网缓存只有 32 条（内存） | 长时间断网会丢最老的数据 | 网关加 SPIFFS/SD 卡；或缩短断网时的上报频率 |
| 单网关容量有限 | 实测 4 路稳定；再多要看信道与共存 | 多网关（`gw02`），云端按网关分组 |
| 无用户账号体系 | 只有一个网页口令 | 加多用户登录/权限；加 Cloudflare Access 邮箱验证（原方案已支持） |
| 没做固件 OTA | 换参数要重新烧写 | CH573F 支持 IAP/OTA，可做"云端下发新固件"（毕设扩展点） |
