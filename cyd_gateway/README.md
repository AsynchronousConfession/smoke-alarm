# 烟雾报警网关 —— CYD (ESP32) 移植版

把原工程 `D:\smoke-alarm\04\gateway_esp32s3`（ESP32-S3）的网关固件移植到
**ESP32-2432S028R (CYD，经典 ESP32，4MB flash，串口 COM13)**。

目标：让这块带屏的板子取代原来的 S3 网关 —— 既保持原有的 BLE 采集 + WiFi + MQTT 上云链路，
又能把节点数据直接显示在屏幕上、并把控制按钮做成本地触控。

## 一、与原工程的关系

`main/` 下的 5 个原工程文件全部复制而来，**只改了 `gateway_main.c` 和 `main/CMakeLists.txt`**
（改动都带 `[CYD port]` 注释），其余 4 个文件与原工程**逐字节一致**：

| 文件 | 状态 |
| --- | --- |
| `node_proto.h` / `wifi_mqtt.c` / `wifi_mqtt.h` / `app_config.h` | 与原工程完全一致 |
| `gateway_main.c` | ①+`esp_system.h` 与状态表内存打印；②BLE 连接前先停扫描、连上后恢复扫描（见第五节）；③节点槽位加"最后收帧时刻"；④新增 `gw_view.h` 的界面读取接口；⑤`app_main` 末尾挂上屏幕与界面 |
| `main/CMakeLists.txt` | 加入屏幕/界面/字库源文件 |

所以原工程**没有被改动**，两边可以直接 diff。协议、MQTT 主题、JSON 字段、断网缓存、
遗嘱消息、云端下发路径全部沿用原实现 —— 服务器和网页不需要任何改动。

## 五、移植中必须改的一处 BLE 逻辑（经典 ESP32 单射频）

第一次烧进 CYD 后，扫描能发现节点、但**连接一直建立不起来**：

```
GW: 发现节点 AA:BB:CC:DD:EE:01 (类型 0) → 分配为 节点1, 正在连接…
GW: │ 节点1  连接中 AA:BB:CC:DD:EE:01  RSSI=0 dBm (等数据)     ← 卡住 20 秒以上
W (92729) BT_L2CAP: L2CA_CancelBleConnectReq - no connection pending
W (92729) GW: ✘ 节点1 (AA:BB:CC:DD:EE:01) 连接断开, 原因 0x00   ← 然后无限重试
```

原因：原工程在扫描回调里**直接发起连接，同时保持扫描不停**（扫描占空比 50%）。
ESP32-S3 的控制器能同时处理扫描与连接建立，而**经典 ESP32 是单射频**，
发起连接的窗口会被扫描抢占，最终连接超时失败。

改法（`gateway_main.c`，均带 `[CYD port]` 注释）：

1. 发现目标后不立即连接：记下待连地址 → `master_stop_scan()`
2. 在 `ESP_GAP_BLE_SCAN_STOP_COMPLETE_EVT` 里（扫描真正停止、射频让出后）再 `esp_ble_gattc_open()`
3. 连接成功后 `master_start_scan()`，继续发现其它节点

改完立刻成功：`节点1 已就绪`，遥测每 2 秒一帧稳定上报，同时扫描仍在继续找其它节点。

### 阶段 2 踩到的两个坑

1. **IRAM 溢出 3600 字节（链接失败）**
   `iram0_0_seg overflowed`。WiFi（默认开了 `ESP_WIFI_IRAM_OPT` / `ESP_WIFI_RX_IRAM_OPT`）、
   Bluedroid、LVGL 三者的 IRAM 占用叠在一起就爆了。解决：关掉 WiFi 的两个 IRAM 优化选项
   （`CONFIG_ESP_WIFI_IRAM_OPT=n`、`CONFIG_ESP_WIFI_RX_IRAM_OPT=n`）。
   本工程每 2 秒才几十字节数据，性能影响可以忽略。
2. **内存余量**
   沿用显示工程的 40 行双缓冲时，空闲内存只剩 54 KB。改成 **24 行**
   （`board_config.h` 的 `LVGL_BUF_LINES`，双缓冲 ≈ 23 KB）后回到 69 KB。

### 界面读取数据的方式

界面不直接碰网关内部结构，只调用 `gw_view.h` 的只读快照接口（实现在 `gateway_main.c`）：

```c
gw_node_view_t nodes[GW_MAX_NODES];
int n = gw_nodes_snapshot(nodes, GW_MAX_NODES);   /* 含 编号/标签/MAC/RSSI/ADC/Rs/Δ%/四种标志/最后收帧时刻 */
```

`gw_send_cmd_to_index()` 也是复用云端下发的同一条路径（走 `on_cloud_command()`），
所以屏幕上下发的指令和网页上下发的完全等价，回执也照样上报云端 —— 阶段 3 的控制页直接用它。

### 卡片布局是怎么定下来的（避免文字叠字）

第一版把 28px 的 Δ% 大字放在卡片右侧，结果大字和右侧的状态徽标/信息行视觉上挤在一起。
靠估算改了两轮都没把握，最后改用"拿数据说话"的三步：

1. **设备端坐标**：在界面上加一段临时诊断，把每个控件的真实位置打印出来
   （`lv_obj_get_coords()`）。实测第一版：名称/徽标行 `y=34..57`、大字行框 `y=30..71`、
   信息行 `y=68..91` —— 大字行框高达 42px，几乎顶到下面那行。
2. **字体墨迹范围**：从生成的字体文件里直接读出每个字形的墨迹位置。LVGL 的摆放公式是
   `墨迹顶端 = (line_height - base_line) - box_h - ofs_y`。28px 数字字体的
   `line_height` 是字体的 ascent+descent = **42**（数字本身只有 21px 高），
   多出来的空白就是挤压的根源。
3. **按数据重排**：大字换成 **22px**，并用新增的 `--line-height` 参数把行高从 33 收紧到 **26**
   （`gen_lvgl_font.py --size 22 --line-height 26`）；卡片高度 68 → 72，
   三行改为：名称/徽标（24）→ Δ% 大字（26）→ ADC/Rs/信号（24）。

重排后的实测坐标（设备自己打印的）：

```
name  y=30..53    badge y=30..53      行框 24px
dpct  y=55..80                        行框 26px（墨迹 58..73）
info  y=75..98                        行框 24px（墨迹 82..93）
卡片  4..235 × 27..98
```

墨迹之间的空隙 8~9px，互不重叠。信息行文字也按实测宽度调整过：
`ADC 246 · 15.7kΩ  -55dBm` 实测 206px，卡宽 232px，留 18px 余量。
这段坐标诊断留在 `ui.c` 里（开机打印一次），以后改布局可以直接看。

## 十一、报警时反复断连的 bug（已定位修复）

**现象**：节点数据一旦超过阈值（进入报警），网关就开始反复断开重连。

### 定位过程

1. 抓串口日志：只有断开/重连，**没有 panic** → 不是崩溃，是链路被打断
2. 关键线索在连接参数日志里：`interval=100 (125ms), timeout=100` →
   节点协商出来的**监督超时只有 1 秒**（错过 8 次连接事件就断）
3. 读 `wifi_mqtt.c` 的发布路径：用的是 `esp_mqtt_client_publish()`
4. 翻 ESP-IDF 源码 `mqtt_client.c`：这个函数**在调用者的任务上下文里直接写 socket**
   （函数体里就是 `while (sending) { esp_mqtt_write(client) ... }`），即**阻塞调用**
5. 而网关的遥测上云是在 **BLE 的 GATTC 回调任务**里发起的

于是链条闭合：报警后上报速率从 0.5 帧/秒变成 **2 帧/秒**，一旦 WiFi 侧写入变慢
（经典 ESP32 是单射频，还要和 50% 占空比的 BLE 扫描抢），BLE 回调任务被阻塞 →
软件共存仲裁得不到调度 → BLE 链路错过那 1 秒的监督超时 → 断链 → 重连 → 再阻塞 → 循环。

> 原 S3 网关同样有这段代码，只是 S3 射频/共存条件更宽裕，没在这个速率上暴露出来。

### 修复

| 改动 | 说明 |
| --- | --- |
| **`mqtt_pub()` 改用 `esp_mqtt_client_enqueue()`** | 只把消息放进发送队列，真正的 socket 发送交给 MQTT 任务，**调用方立即返回**。这是根因修复 |
| 扫描窗口 30ms → 15ms（占空比 50%→25%） | 少抢射频，给已建立的连接和 WiFi 让路 |
| 请求更宽松的连接参数（30~50ms 间隔 / 4s 监督超时） | 加分项；节点固件会把自己的参数再要回去，所以不是关键 |
| `gw_log_push()` 的 `time()` 移到临界区外 | `time()` 可能走 libc 锁，不该在关中断状态下调用 |

### 修复后的验证

- 遥测上云正常：16 秒收到 8 条 `tele`，`seq` 连续（改成 enqueue 没有引入回归）
- 新增"遥测处理耗时探针"：处理超过 50ms 会打印告警（`[节点N] 遥测处理耗时 xx ms`），
  以后任何阻塞都会被立刻抓到

> 判定标准：报警期间**不应该**再出现 `✘ 节点N 连接断开` 与 `连接参数已更新` 反复刷屏。

### 【更正】真正的崩溃点：临界区里调用了 `localtime_r()`

上面那套"publish 阻塞"的推断**不是本次故障的主因**。报警时抓到的日志显示：报警行之后紧跟一行
`Backtrace:` 而**没有** `Guru Meditation` 字样 —— 这是 `abort()` 型崩溃的特征。用
`xtensa-esp32-elf-addr2line` 解码后，调用链是：

```
lvgl_port_task → lv_timer_handler → ui_refresh → refresh_records
  → gw_log_alarm_today → count_by_type           (gw_log.c)
    → localtime_r → _tzset_unlocked → lock_acquire_generic → abort()
```

原因：`count_by_type()` 遍历事件时是**在 `taskENTER_CRITICAL()` 里**调用 `localtime_r()` 的。
newlib 的 `lock_acquire_generic()` 会检测"关中断状态下申请锁"并直接 `abort()`
（`components/newlib/locks.c:130`）。

这解释了两个现象：

1. **只有报警时才崩**：`localtime_r()` 只在日志里真的存在报警事件时才会被调用；
   平时日志里没有 alarm 事件，循环直接跳过，永远走不到那一行
2. **重启后又"恢复正常"**：事件日志在 RAM 里，重启即清空，于是要等下一次新的报警跳变才再崩一次 ——
   从外部看就是"一超过阈值就反复断开重连"

修复：把 `time()` / `localtime_r()` / `mktime()` 全部移到临界区**之外**，
先算出"今天 00:00 的时间戳"，临界区里只做数值比较。

### 顺带做的加固（都是真实风险，但不是本次主因）

| 改动 | 说明 |
| --- | --- |
| `mqtt_pub()` 改用 `esp_mqtt_client_enqueue()` | `esp_mqtt_client_publish()` 会在调用者任务里直接写 socket；遥测是在 BLE 回调里发的，阻塞它会危及 BLE 链路。enqueue 只入队、立即返回 |
| 扫描窗口 30ms → 15ms | 经典 ESP32 单射频，降低扫描占空比给连接和 WiFi 让路 |
| `gw_log_push()` 的 `time()` 移出临界区 | 同样是"临界区里调 libc"的隐患 |
| 遥测处理耗时探针 | 超过 50ms 打印告警，任何回调阻塞都能立刻发现 |

## 十三、传感器型号与"数据含义"显示（新增）

节点固件把 `node_cfg.h` 的 `NODE_MODEL` 放进信息帧（`编号|型号|版本`）上报，
网关本来就把它存进 `s_slot[].model` 并经 `gw_view.h` 暴露给界面，这次只是把屏幕用起来：

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 监控卡片第 1 行 | `节点1 N01` | `节点1 N01 · MQ-135`（型号来自信息帧） |
| 监控卡片大字 | 只有 `Δ% -6.6%` | 大字右边多一个含义标签：空气质量 / 氨气浓度 / 烟雾·可燃气 |
| 曲线详情标题 | `节点1 N01` | `节点1 N01 · MQ-135` |
| 详情页 Δ% 标题 | `Δ% 曲线（±25% 报警线）` | `Δ% 曲线（空气质量 ±25%）` |
| 详情页 Rs 标题 | `Rs 曲线（kΩ，自动缩放）` | `Rs 曲线（越低浓度越高）` |
| 详情页底部 | `每帧 1 点（2 秒）· 最多 60 点` | 该型号的说明，如 `氨气/苯/烟雾越浓，Δ% 越负` |

对照表在 `main/ui.c` 的 `s_sensors[]`（现有 MQ-135 / MQ-137 / MQ-2 / MQ-7，最后一行 `NULL` 是兜底），
加新型号只加一行。三种传感器的**读数含义是同一种**：Rs 越小 → 被测气体越浓；Δ% 是 Rs 相对
自适应基线的变化率，所以 Δ% 越负表示浓度越高（判据取绝对值）。

### 顺带修掉的一个字形缺失

原字库缺少 `±`（U+00B1），所以 `Δ% 曲线（±25% 报警线）` 里的 ± 在屏上一直是个空心方框
（LVGL 会打印 `glyph dsc. not found for U+00B1`）。原因是字表 = ASCII + GB2312 一级汉字 +
`DEFAULT_PUNCTUATION` + 扫描源码里的非 ASCII 字符，而这份字库生成于那行文案加进 `ui.c` **之前**。
同一条命令重跑一次即可（重跑时它会扫到 ±）：

```powershell
cd tools
python gen_lvgl_font.py --font NotoSansSC-Regular.otf --size 16 `
    --name lv_font_noto_sc_16 --extra-scan ..\main --line-height 20 `
    --out ..\main\fonts\lv_font_noto_sc_16.c
```

> `--line-height 20` 不能省：整套布局（卡片行高 20 / 大字 24）是按 line_height=20 排的，
> 不带它会回到 24，卡片立刻溢出。生成脚本结尾会打印 `line_height=20, base_line=5` 自检。

## 十四、产品化 阶段 1：等级 / 指数 / 趋势 + 探头自检（已完成）

目标：屏幕上不再堆工程参数（Δ% / Rs / ADC），而是家里人会看的东西。

### 监控卡片改成三行

| 行 | 内容 |
| --- | --- |
| 第 1 行 | `节点N 房间名 · 传感器`（左） + **等级徽标**（右） |
| 第 2 行 | **指数**（0~100 大字） + **等级色条**（长度=指数、颜色=等级） + **趋势**（↑变差 / →平稳 / ↓好转） |
| 第 3 行 | `Δ -6.6% · 12 秒前`；**报警时右边出现"消音"按钮**（走和云端下发同一条路径） |

等级词按传感器类型分开（`main/ui.c` 的 `s_sensors[]` + `level_word()`）：

| 类型 | 型号 | 等级词 |
| --- | --- | --- |
| 安全类 | MQ-2 / MQ-7 | 正常 / 注意 / 报警 |
| 环境类 | MQ-135 / MQ-137 | 优 / 良 / 轻度 / 中度 / 重度 |

指数换算：`指数 = clamp(|Δ%| × 100 / 报警线, 0, 100)`，即 **100 正好是节点自己的报警线**（25%）。

顶部状态条也跟着换了：**报警 > 探头异常 > 一切正常** ——
`厨房 可燃气 报警` / `2 个探头异常 · 请检查接线` / `一切正常 · 网络正常 · 3/4`。

### 探头自检（这次最重要的改动）

**为什么必须有**：探头没接时 PA4 悬空，会读出一个"纹丝不动"的贴轨值（实测三路
ADC 分别恒为 4073 / 4061 / 4066，44 帧一个值都不变）；而 Δ% 又被自适应基线慢慢拉到 0，
屏幕上就显示 **0.0% + 正常**——**假安全**，这在家用产品里不能接受。

判据（在 `gateway_main.c` 的 `handle_telemetry_frame()`，**不用改节点固件**）：

```
连续 14 帧（约 28 秒）ADC 完全相同  且  贴在电源轨（>=4000 或 <=8）  →  探头故障
```

真探头有热噪声，30 秒内不可能一帧不差；读数恢复后自动清除（日志打印"探头读数恢复正常"）。
实测三路全部正确报出 `探头疑似未接/故障: ADC 连续 14 帧 = 4073（贴轨且零抖动）`。

### 实测

| 项目 | 结果 |
| --- | --- |
| 布局自检 | 开机 + 有数据后共 7 轮，**无一处文字越界**；色条实测 `x=91..196 (w=106)`，趋势右对齐 `x≈210..226` |
| 探头自检 | 3/3 正确报故障（28 秒内） |
| 空闲内存 | **38~40 KB**（加卡片控件前 52 KB，历史最低 28 KB） |
| 稳定性 | panic 0、错误 0 |

> 内存从 52 KB 降到 ~39 KB（每张卡片多了 8 个控件）。目前够用，但如果后面还要加
> 设置页 / 迷你柱状图，建议先把第 2 行的趋势箭头或色条合并掉一个。

### 还留着的一个排查开关

`gateway_main.c` 顶部的 `GW_TRACE_FRAMES` 现在是 **1**：串口逐帧打印
`TRACE 节点N seq=.. fl=0x.. adc=.. ao=..mV rs=.. D=..`（`fl` 的 bit1 = 节点预热位）。
接探头时用它一眼就能看出有没有真实信号（**有信号 = ADC 会抖**），排查完改成 0 即可。

## 十六、产品化 阶段 3：环境类改用 Rs/R0 绝对基准 + 清洁空气标定（已完成）

### 为什么要分两套判据

| 类型 | 型号 | 看什么 | 理由 |
| --- | --- | --- | --- |
| **安全类** | MQ-2 / MQ-7 | **Δ%**（相对自适应基线） | 要抓"几秒内突然出现可燃气"，相对变化最灵敏 |
| **环境类** | MQ-135 / MQ-137 | **Rs / R0**（相对清洁空气的绝对值） | 空气慢慢变差时，自适应基线会跟着漂，Δ% 永远接近 0，屏幕就永远显示"优" |

> 比值 `Rs/R0` 有个额外好处：公式里模块的负载电阻 RL 会约掉，供电电压的误差也基本抵消，
> 所以**换探头、换模块批次只要重新标定一次 R0**，读数含义仍然一致。

### 怎么标定（控制页新增"标定"按钮）

1. 把该节点放在**清洁空气**里（室外/通风房间）稳定几分钟；
2. 屏幕 → **控制** → 点选那个节点 → 点 **标定**；
3. 状态行显示 `节点1 已标定 R0=12345Ω`，卡片从"未标定"变成真实的 优/良/轻度/…

标定值按 **节点 MAC** 存进 **NVS**（命名空间 `cal`，key = MAC 小写，value = R0 欧姆），掉电不丢；
换探头要重新标定。开机还会做一次"写-读-删"的 NVS 通路自检（只动保留 key `0000deadbeef`）。

**会拒绝标定的情况**（宁可拒绝也不写错值）：

| 情况 | 提示 |
| --- | --- |
| 节点还没上报数据 | `失败：节点还没上报数据` |
| **探头自检不通过**（阶段 1 的判定） | `失败：探头异常，先接线` |
| Rs 离谱（<100Ω 或 >900kΩ） | `失败：读数异常 Rs=…Ω` |
| NVS 写入失败 | `失败：写入 NVS 出错` |

### 指数映射（环境类，ratio_min = 30%）

| Rs/R0 | 指数 | 等级 |
| --- | --- | --- |
| ≥ 86% | 0~19 | 优 |
| 74~86% | 20~39 | 良 |
| 58~74% | 40~59 | 轻度 |
| 44~58% | 60~79 | 中度 |
| < 44% | 80~100 | 重度 |

卡片第 3 行也会直接给出绝对值：`Rs/R0 0.85 · 12 秒前`。

### 未标定的环境节点

不显示假的"优"，徽标显示 **`未标定`**、指数 `--`，第 3 行提示 `请在清洁空气里点 标定`。
安全类（MQ-2）**不需要标定**，照旧走 Δ%。

### 实测

| 项目 | 结果 |
| --- | --- |
| 启动日志 | `CAL: 还没有任何标定数据（第一次上电属于正常）` → `CAL: NVS 读写自检: 通过` |
| 控制页 | 2×2 节点 + 2×2 操作（消音/自检/复位/标定），布局自检无越界 |
| 探头自检 | 3/3 仍正确报故障（故障优先于"未标定"） |
| 空闲内存 | **38~39 KB**（历史最低 31 KB） |
| 稳定性 | panic 0、错误 0 |

### 已知限制 / 下一步

1. 环境类的"重度"只在屏幕上变红，**不触发蜂鸣器、也不发云端报警事件**——空气差是"提醒"不是"火灾"。
   如果要做成"超标告警"，需要在网关侧按标定比值再造一条报警路径（含云端事件与消音）；
2. 标定目前只存在网关本地 NVS 里，**没有上报云端**（换网关要重新标定）；
3. ~~设置页 / 开机自检页 / 报警弹窗~~ → 已在**阶段 4** 完成，见下一节。


关掉时用 `lv_obj_del()` **把整页对象删掉、内存还回去**（开机自检只需要一次，
没必要常驻）——实测日志：`开机自检页关闭，对象已回收`。

### 3. 报警自动弹大屏

任何一路**真的报警**（探头故障不算）→ 全屏半透明遮罩 + 中央红闪卡片：

| 元素 | 内容 |
| --- | --- |
| 红闪横幅 | `报 警`（横幅底色和卡片边框在两种红之间 500ms 交替） |
| 房间行 | `厨房 · 可燃气` |
| 数值行 | `Δ% -32.1%   峰值 42.0%`（>100% 的异常值显示成 `峰值 >100%`） |
| 提示行 | `请立即查看并通风` |
| 按钮 | **消音**（下发 `M` + 本机静音 60 秒）/ **关闭** |

- 点"关闭"或"消音"后，**本次报警不再自动弹**；
- 报警全部解除后自动收起，并重新恢复"下次报警还会弹"；
- 弹窗和曲线详情页都在 `lv_layer_top()` 上，弹出时用 `lv_obj_move_foreground()` 保证在最前面。

### 4. 事件持久化（这次刻意没做）

原计划把事件记录写进 SPIFFS，最后决定**先不做**，理由：

1. **云端已经在持久化**：报警/解除事件随 MQTT 上报，服务器 `server/data/iot.db`（SQLite）里有完整历史，网页也看得到——本机再存一份是重复；
2. SPIFFS 反复擦写有寿命问题，为一个"重启后还能看今日次数"的功能不值得；
3. 真要做，正确形态是**从云端拉回历史**，而不是本机自己攒。

### 5. 实测

| 项目 | 结果 |
